# 0019. Check in generated protobuf code and serve REST through a runtime transcoder

- Status: Accepted
- Date: 2026-11-18

## Context

[ADR 0006](0006-protobuf-contracts-grpc-api.md) makes protobuf the API source of truth, served as
gRPC, with "a REST/JSON gateway and an OpenAPI document both generated from the same contracts", and
leaves the tooling to the system design. Constraints from the workspace guardrails:

- `cargo xtask arch` bans `include!`, so the usual `build.rs` + `include!(OUT_DIR)` pattern is not
  allowed;
- the strict workspace lints (`missing_docs`, clippy `pedantic`) apply to every crate, and module-wide
  `expect` and any `allow` attribute are rejected, while tonic's generated code carries module-level
  `allow` attributes;
- no mature Rust grpc-gateway exists; `tonic-rest` fails `deny.toml` (it pulls `chrono`), and
  `pbjson-types` pulls `chrono` too.

REST options: `tonic-rest`; connectrpc (RPC-style URLs, not resource-style); full code generation of
axum handlers (about 1.5k lines of generated code under the lints); a runtime transcoder driven by
the descriptor set ([system design §5.7](../design/system-design.md#57-codegen-rest-gateway-versioning-and-the-cli)).

## Decision

- **Rust code generation** uses `protox` (no `protoc`), `tonic-prost-build` and `pbjson-build`, with
  well-known types mapped by hand. `cargo xtask codegen` writes the output into the generated roots
  listed in `architecture.toml`: `crates/racksmith-proto/src/gen/` for the public API,
  `crates/racksmith-rsimg/src/gen/` for the signed `racksmith.rsimg.v1` manifest and
  `crates/racksmith-storage-model/src/gen/` for the internal `racksmith.storage.v1` encoding. All are
  checked in; `cargo xtask codegen --check` fails CI when any is stale. There is no `build.rs`, and no
  prost type is written by hand.
- **Generated code passes the lints without weakening them:** the codegen post-processor rewrites
  module-level `allow` attributes into item-level `#[expect(…, reason = "generated by
  tonic-prost-build")]` on exactly the items that trip a lint, and `buf lint` with the `COMMENTS` rule
  requires a doc comment on every proto element, which satisfies `missing_docs`. A week-1 spike proves
  the first generated module passes `cargo xtask ci`; F1 depends on it. A narrowly scoped
  `generated` path exemption would need its own ADR and is the last resort, not the plan.
- **REST gateway:** `cargo xtask codegen` also generates a static route table (HTTP method, path
  template, body field, RPC) from the `google.api.http` annotations. At runtime one axum handler
  matches the table, transcodes JSON through `prost-reflect` `DynamicMessage` and the embedded
  descriptor set, and calls the tonic service in process, behind the same authn/authz layer as gRPC.
  Server streams become NDJSON as stretch work.
- **OpenAPI 3** is generated in CI by `buf generate` with gnostic `protoc-gen-openapi` and checked in.
- **Contract checks:** `buf lint` and `buf breaking` against `main`, with `ignore_unstable_packages`;
  `racksmith.options.v1` and `racksmith.rsimg.v1` are stable from day one. `cargo xtask proto-check`
  rejects RPCs without a policy option, sensitive fields reachable from responses, and resources
  without `ObjectMeta`.

## Consequences

- No toolchain surprises for contributors, and generated code is reviewable in diffs.
- The REST surface stays small (about 800 hand-written lines plus a generated table) and cannot expose
  anything gRPC does not.
- This reads ADR 0006's "generated from the contracts" as "derived from the contracts by a generated
  table and a descriptor-driven transcoder". **The owner must confirm that reading**; full handler code
  generation is estimated at one to two more weeks.
- prost drops unknown fields on decode, which bounds the reversibility promise of
  [ADR 0009](0009-embedded-store-behind-trait.md): downgrades rely on explicit `down` migrations.
